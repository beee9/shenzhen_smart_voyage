# 记忆模块设计建议

本文档基于对 `memory.py` / `chat_service.py` / `api_server.py` 现状的分析，
给出 `user_profile`、`current_task`、`entity_history` 三类记忆的重新设计方案，
以及表结构与数据库选型的建议。`short_term_messages`（短期记忆）现状实现完整，不在本文讨论范围内。

## 一、现状问题回顾

| 记忆类型 | 写入时机 | 存的内容 | 持久化 | 重启恢复 |
|---|---|---|---|---|
| short_term_messages | 每轮对话自动 | 完整对话 | 有 | 有 |
| user_profile | 仅手动调 API | 结构合理 | 有 | 有 |
| current_task | 命中 6 种意图时自动 | `{type, query}`，跟 entity_history 重复 | **无** | **无** |
| entity_history | 命中 6 种意图时自动 | `{type, query}`，并非真实体，只是意图+原句 | 有（query_history 表） | 有 |

核心问题：`current_task` 和 `entity_history` 名不副实，两者存的是同一份"意图分类 + 原始问句"，
没有做真正的结构化信息抽取；`user_profile` 只有"读"和"持久化"，没有"对话中自动写入"这一环。

## 二、设计原则

1. **各记忆职责要分开，不能互相重复存同一份东西。**
   - `entity_history`：记录从查询中抽出的结构化实体（出发地、到达地、日期、人数等），可跨轮引用。
   - `current_task`：记录"当前这轮任务"的状态机（还缺什么信息、执行到哪一步了），有生命周期，用完要清空。
   - `user_profile`：记录长期稳定的用户偏好，变化频率低，供多次对话复用。
2. **抽取尽量复用已有的 LLM 调用，不为了记忆单独加调用**，避免拖慢响应、增加成本。
3. **写入要异步/不阻塞主响应**，抽取出错不能影响正常回复。
4. **持久化统一走 MySQL**，理由见第四节；用 JSON 列解决半结构化字段的问题，不需要额外引入别的数据库。

## 三、逐项设计

### 3.1 entity_history（结构化实体记忆）

**目标**：记住"用户提到过深圳出发、11 月 5 日、2 人"这类结构化信息，供后续代词消解
（"那趟车""换一天"）和统计使用。

**写入时机与逻辑**：
不新增 LLM 调用，而是扩展现有的 `intent_prompt` 输出。让 `intent_agent` 在识别意图、改写查询的
同时，顺带按每个意图输出结构化槏位（slots），例如：

```json
{
  "intents": ["train"],
  "user_queries": {"train": "深圳到上海11月5日的高铁"},
  "slots": {"train": {"departure_city": "深圳", "arrival_city": "上海", "date": "2026-11-05", "passenger_count": 1}},
  "follow_up_message": ""
}
```

`chat_service.py` 里原来调 `extract_entities(intent, query_str)` 的地方，改成传
`extract_entities(intent, slots.get(intent, {}), query_str)`，把 `slots` 结构化字典存进去，
`query_str` 只作为原文兜底（用于 slots 抽取失败时仍有可读记录）。

**读取**：`get_recent_entities(intent_type=None, limit=5)`，按需取最近几条结构化实体，
拼进 `intent_prompt` 帮助代词消解，或供 `_call_agent_intent` 里"信息缺失时自动补全"使用。

**持久化表设计**（替换现在的 `query_history`，其实那张表更适合改名为“查询日志”单独保留做审计）：

```sql
CREATE TABLE IF NOT EXISTS entity_history (
    id INT AUTO_INCREMENT PRIMARY KEY,
    intent_type VARCHAR(30) NOT NULL COMMENT '意图类型',
    slots JSON NOT NULL COMMENT '结构化实体字段，如出发地/到达地/日期/人数',
    raw_query TEXT COMMENT '原始查询，兜底展示用',
    created_at DATETIME NOT NULL,
    INDEX idx_intent_time (intent_type, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**重启恢复**：`load_entities_from_db()` 按 `created_at DESC LIMIT 20` 取回，`JSON` 列用
`json.loads` 还原成 dict，反转成时间正序装入 `entity_history`。逻辑跟现在的 `load_entities_from_db`
基本一致,只是多一步 JSON 解析。

### 3.2 current_task（任务状态机）

**目标**：处理"信息不全，需要追问，下一轮接着填"的场景。现状 `intent_prompt` 已经有
`follow_up_message` 机制，但追问之后用户补充的信息完全靠对话历史文本重新走一遍意图识别，
没有真正"记住我还缺什么"。

**结构设计**：不再是 `{type, query}`，改成带生命周期的任务对象：

```python
current_task = {
    "task_id": "uuid",
    "intent": "train",
    "status": "collecting",  # collecting / executing / completed / cancelled
    "slots": {"arrival_city": "上海"},       # 已收集到的槏位
    "missing_slots": ["departure_city", "date"],  # 还缺的槏位
    "created_at": "...",
    "updated_at": "..."
}
```

**写入时机与逻辑**：
- 意图识别返回 `follow_up_message` 非空时（说明信息不全）：创建或更新 `current_task`，
  写入已知 slots 和缺失字段，状态设为 `collecting`。
- 下一轮用户输入时，`intent_agent` 的 prompt 里注入 `current_task`（现状已经有这行，
  chat_service.py:89 `task_context` 参数），让大模型知道"正在收集 train 任务的 departure_city"，
  结合新输入补全。
- 一旦某个意图真正执行成功（`_call_agent_intent` 正常返回，非"暂不支持""执行失败"），
  就调用 `complete_task()`，把状态置为 `completed` 并清空 `current_task`（或者只保留最后一条
  归档，内存态清空），避免"最后一次任务"永久占着当前上下文误导下一轮无关对话。

**持久化表设计**（新增，现状完全没有）：

```sql
CREATE TABLE IF NOT EXISTS current_task (
    id INT AUTO_INCREMENT PRIMARY KEY,
    task_id VARCHAR(36) NOT NULL,
    intent VARCHAR(30) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'collecting',
    slots JSON NOT NULL,
    missing_slots JSON,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE KEY uniq_active_task (status)  -- 简化：全局只允许一条非 completed 记录，见下方说明
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

说明：如果要严格保证"同时只有一个进行中任务"，`UNIQUE KEY` 用 status 做唯一键并不严谨（MySQL
唯一键允许多个 NULL 但不允许多个相同非 NULL 值，多条 completed 记录会冲突）。更稳妥的做法是不加
这个唯一约束，改为应用层保证：每次创建新任务前，先把旧的未完成任务标记为 `cancelled`。
表结构上只留 `INDEX idx_status (status)` 方便查询当前进行中的任务。

**重启恢复**：`load_task_from_db()`，取 `status IN ('collecting', 'executing')` 的最新一条
恢复到内存 `current_task`；没有则保持空字典。

### 3.3 user_profile（长期偏好）

**目标**：记住"喜欢靠窗""预算中等""不吃辣"这类跨会话都成立的偏好，现状持久化机制可用，
缺的是自动写入。

**写入时机与逻辑**：
在 `chat()` 方法里，助手生成回复之后（`self.memory.add_message("assistant", response)` 之后），
异步触发一次偏好抽取，不阻塞返回给用户的响应：

```python
asyncio.create_task(self._extract_profile_async(user_input, response))
```

`_extract_profile_async` 内部用一个新的轻量 prompt（`profile_extraction_prompt`），输入本轮
user_input + assistant response，输出"本轮是否包含可沉淀的偏好，以及偏好的 key/value"，
是则调用 `update_profile()`。要点：

- 只在明确表达偏好时才写（"我喜欢靠窗""预算控制在 2000 以内"），避免把临时性query（"帮我订
  今天的票"）误当成偏好。prompt 里要求模型没有把握就返回空 dict。
- 抽取失败或返回格式不对时静默跳过，不影响主流程，记 warning 日志即可。
- 同 key 更新按覆盖处理（座位类型这种单值偏好），但像"忌口""常去城市"这种应该是多值列表，
  需要 `update_profile` 区分 merge 策略——建议 value 统一存 JSON（见下方表结构），
  单值直接覆盖、列表类做 union 去重。

**持久化表设计调整**：现状 `profile_value VARCHAR(200)` 只能存字符串，多值偏好会被
拼接成字符串损失结构。建议：

```sql
CREATE TABLE IF NOT EXISTS user_profiles (
    profile_key VARCHAR(50) NOT NULL PRIMARY KEY,
    profile_value JSON NOT NULL COMMENT '单值或列表，如 "二等座" 或 ["不吃辣","不吃海鲜"]',
    source VARCHAR(20) DEFAULT 'auto' COMMENT 'auto=对话中抽取，manual=用户在前端手动填',
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

加 `source` 字段是为了区分自动抽取和手动编辑，前端偏好面板可以标出"这条是 AI 猜的还是你自己填的"，
用户发现抽取错了可以针对性删除自动来源的记录，而不影响手动配置。

**读取**：现状 `get_profile_text()` 逻辑不用大改，多值时用 `、` 连接展示即可。

## 四、数据库选型结论

**继续用 MySQL，不需要引入新的数据库类型。**

- `short_term_messages`、`current_task`：强结构化、行数很小、有明确顺序/状态字段，关系型数据库是最自然的选择。
- `user_profile`、`entity_history`：字段模式因意图不同而变化（train 有座位类型，tour_group 有预算/天数），
  但 MySQL 5.7+ 的 `JSON` 列类型足够承载这种半结构化数据，还能保留主键、索引、事务这些关系型数据库的能力，
  没必要为此换 MongoDB 之类的文档数据库——那样反而要多维护一套连接、备份、运维体系。
- 唯一可能超出关系型数据库能力范围的场景是**语义模糊召回**：比如"看看用户之前问过类似的问题"，
  这种按语义相似度而非精确字段匹配的检索，MySQL 做不到，需要向量数据库（如 pgvector/Milvva/Chroma）
  配合 embedding。但这是锦上添花的功能，现阶段业务量和需求都不需要，可以先不做，
  等以后确实要支持"语义相似历史召回"再作为 MySQL 之外的补充索引引入，而不是替代关系型存储。

## 五、改造优先级建议

1. **user_profile 自动写入**：收益最直接（用户体验上能感知到"记住我了"），改动集中在新增一个
   抽取 prompt + 异步调用，风险最低，建议先做。
2. **entity_history 结构化**：需要改 `intent_prompt` 输出格式，涉及意图识别主链路，改动面稍大，
   但收益是能支撑代词消解，值得做。
3. **current_task 状态机**：改动最大（新表、新生命周期管理、清空时机),收益是能更好处理多轮追问，
   可以放在最后，且可以先用最简单版本（内存态 + 定期持久化，不做严格单任务约束)验证效果再迭代。
